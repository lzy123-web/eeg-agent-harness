## 根因与设计选择

已有原生证据：Issue58 v2 T07第12提案明确引用合法Epoch生产者，却因修订预检只查本交付旧输出而拒绝；既有临时注入证明遗漏见证，但不是完整修复。范围继承、执行参数装配、修订预检、交付匹配分别选择来源，使同一对象存在不同解释；拟修订生产者仍从旧图取结果还会产生错误就绪风险。T05重建已有任务、错字段层级/漏标量fields另属接口使用和模型选择问题，不与T07混因。

比较：只在revise分支补生产者会保留其他入口分歧；强制规划时全部实际结果存在会拒绝合法未来依赖；自动猜来源/改写计划或新增第二状态库会破坏责任边界。选择复用原PlanGraph/Store的**只读科学绑定解析**：分别标记用户声明、指定版本InputRef、本交付旧结果、实际执行回执/明确工件；返回统一对象、范围、来源依据和待定/冲突原因。只从明确引用解析，不扫描相似档案。实际状态仍仅归原图/Store所有。

计划登记可保留合法未来依赖和缺参，执行仍须实际输入/控制前提就绪，完成仍须真实结果与科学接受；三个阶段不合成一个布尔值。修订在拟提交事务图上只读解析，当前引用不能偷用被修改生产者旧输出，固定历史引用仍指原版本。声明与真实工件冲突、多来源含混、错record/版本/时基必须拒绝；同一对象的重复明确来源可去重，但保留全部来源轨迹。

本阶段后续将记录具体实现、原生重放/受控合法链/独立反例、真实会话、版本、实际送达回答及预算，不提前宣称通过。Issue58已接受执行回执和Issue57接受生命周期保持必要回归。
